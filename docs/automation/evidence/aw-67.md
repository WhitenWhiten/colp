# AW-67 — extension: browser rules at save, below the account's rules

Built on the Q7 decision (`d28ed7a9`) on `main`. Design [01 §7.5](../design/01-architecture.md#75-browser-rules-adr-a24-au-34),
ADR-A24, story AU-34; acceptance AC-69 (save path) and AC-70. Shared core `@know-n/colp` 0.2.0, unchanged.

## What shipped

### The rule (`src/automation/browser-rules.ts`)

A browser rule is the M1 placement definition the web editor writes, with no collection scope, plus the
native folder it files into. The example is [browser-rule.json](../design/examples/browser-rule.json).

- **Editor shape.** Name, all/any, and conditions of four kinds: site is, site ends with, title contains,
  URL path starts with. "Has tag" is left out: tags are written after the bookmark exists, so it never
  matches at save (as for account rules, `pre-save.ts`).
- **Checking.** `checkBrowserDraft` returns the definition to store or the problems the editor should
  point at: no condition, more than 8, a value over 512 characters, a site that is not a host, no folder,
  a name over 200 characters. The stored definition passes `validateM1Rule` and holds the evaluator's
  normalized values, so what is stored is what runs.
- **Friendly input.** A pasted link in a site condition stands for its host
  (`https://docs.github.com/en/…` → `docs.github.com`). An unnamed rule is named after its first value.
- **Decision.** `decideBrowserRules` resolves each enabled rule's folder now (gone, a bookmark, or managed:
  unresolved) and runs the shared `evaluateLocalRules` over the same facts the account path builds
  (`preSaveFacts`, origin `sync`, no tags), with priority 100. Outcomes: `placed`, `kept` (a folder the
  Owner picked), `blocked` (the folder is unusable), `conflict` (two rules disagree). `evaluateLocalRules`
  now takes any rule with `ruleId` and `definition` (`EvaluableRule` in `runtime-profile.ts`).

### The store (`src/automation/browser-rule-store.ts`)

Kept in the automation IndexedDB store under its own keys, `known.automation.browserRules.v1` and
`known.automation.browserPlacements.v1`. Nothing in it is sent anywhere.

- Create, edit (keeps id, order, creation time and on/off), switch on/off, remove; at most 100 rules.
- Every change is one read-modify-write taken in turn, so concurrent saves never lose a rule.
- A stored value that fails `validateM1Rule` is dropped on read rather than guessed at.
- The placement log keeps the newest 20 pages a browser rule filed, once per capture id.

### At save (`src/sw/capture.ts`, `src/sw/automation-browser.ts`)

`startCapture` asks the account's rules first. Only when `preSaveDecision` has nothing to say (no account,
no bundle, a paused bundle, another collection, no match) does it ask `browserPreSaveDecision`. Any account
outcome, including `blocked` and `expired`, settles the save.

- **Recorded decision.** `CaptureAutomation` is now `AccountAutomation | BrowserAutomation`. The browser
  variant has `source: 'browser'`, the outcome, the rule's id and name, the matching ids, the folder title
  and the folder it replaced. Tasks saved before this change read as account decisions.
- **Same treatment downstream.** The rule's folder goes through `captureTarget` again; a folder that cannot
  take the save blocks (`blockedPlacement` handles both variants). The save line, the "By rule" mark and
  tags-only local classification read the browser decision exactly as an account one.
- **No receipt.** `recordPreSaveReceipt` logs a browser placement and returns; `wakeCaptures` hands only
  account placements to receipt recovery.
- **Popup preview.** `known.automation.match` answers with the account's decision, else this browser's.
- **Commands.** `known.automation.browser.save | enable | remove` are validated in their exact shape
  (`validBrowserRuleCommand`) and accepted only from the Options page (`trustedLifecyclePage`).

## Limitations

- No Options UI yet: rules are written through the worker commands. AW-68 adds the editor and the
  real-browser run of AC-69.
- Star-button creations stay account-only (design 01 §7.5).
- A browser placement's log entry is written when the save is acknowledged; a worker stop in between loses
  the log line, not the placement.
