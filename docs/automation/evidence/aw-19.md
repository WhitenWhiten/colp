# AW-19 — extension: the pre-save rule path

Built on AW-50 (`0cf80c3`) on `main`. Contract `0.2.1-design`, profile `browser-bounded-v1`, shared core
`@know-n/colp` 0.2.0. The rule under test is the reviewed M1 fixture
([m1-placement.json](../../../packages/extension/tests/fixtures/automation/m1-placement.json)). Stories AU-06,
AU-07 and AU-12; acceptance AC-01, AC-02 and AC-04.

## What shipped

### The decision (`src/automation/pre-save.ts`)

`decidePreSave` evaluates the installed bundle with AW-49's `evaluateLocalRules`, before
`chrome.bookmarks.create`.

- **Facts.** They are the server's facts for a Sync create in this collection:
  - the URL through the core's `normalizeUrl`;
  - the title;
  - the canonical parent and ancestors of the folder the save would otherwise use (`canonicalLocation`);
  - origin `sync`, and no tags.
- **Intent.**
  - An explicit folder choice is `userSelected`, which keeps the user's folder.
  - Remembered and default folders are `userDefault`.
- **Where it applies.** Only rules of the collection this browser syncs are evaluated.
  - No bundle, a paused bundle, another account and another collection: no rule applies.
  - Sync stopped on this browser: no rule applies.
- **Outcomes.**
  - `placed`: the save is created directly in the rule's native folder, with no create-then-move.
  - `kept`: an explicit choice won.
  - `blocked`: the folder is unmapped, deleted, or unusable for saving. The binding reason is
    recorded. If the rule's folder fails the save-target checks, `blockedPlacement` applies.
  - `conflict` and `review`: no placement.
  - `expired`: an out-of-date copy is evaluated only to say so. It never places.

### On every extension save path (`src/sw/capture.ts`)

`startCapture` is the one entry for the manual popup, the Alt+S shortcut (it opens the popup), the
automatic toolbar save, the context menu (page and link) and Save tabs. It calls `preSaveDecision`
after resolving the default target.

- **Placement.** A placement's folder goes through `captureTarget` again, with the same permission,
  subscription and unsupported-folder checks. It then becomes `targetNativeId`, so
  `savePagesThroughNativeIngress` creates the bookmark there.
- **Recorded decision.** The decision is stored as `CaptureTask.automation` (`src/capture/contracts.ts`):
  - outcome and blocked reason;
  - rule id, name, rule revision, binding revision and semantic digest;
  - the matching rule ids;
  - bundle revision and settings revision;
  - satisfied task types (only `classify.root`, and only for a placement);
  - the canonical destination and its title;
  - the folder it replaced;
  - the Sync replica and generation it was made under.
- **Explicit choice (`folderChoice`).**
  - The popup sends `explicit` when the folder is the user's own pick: picked in this popup, or picked
    in an earlier opening this browser session and not yet saved to (`save-folder-ui` `explicit()`).
  - Save tabs sends `explicit` once the user changes its folder select. Older batches count as
    explicit.
  - The automatic popup and the context menu never carry a choice.
- **Receipt.** When a placed save is acknowledged (saved, new), the worker records its AW-50 receipt
  under the capture id as `localReceiptId`. `createReceiptStore.add` is now add-if-absent, so a
  repeated acknowledgement never resets a receipt in progress.

### Classifiers after a rule hit

A rule hit never asks any model for a folder, whatever its outcome.

- **The user's own provider (local).** It is asked for tags only (`folder: false, tags: true`) when the
  tag mode is Suggest or Add. Nothing is sent when the mode is Off.
  - `classificationDocument` takes `folder: false`.
  - `runLocalClassification` honours it. It needs no folders, and returns `local_no_tags` without a
    call when there is no tag vocabulary.
  - `classifyLocalCapture` never moves a rule-placed bookmark, and ends quietly on `local_no_tags`.
  - A user move before the call still wins (`manually_edited`, manual fence).
- **Know-N suggestions (cloud).** Not requested at all: the task's classification is `none`.
- **Popup chip.** `bindPopupClassification` takes `ruleFolder`. While a rule holds the folder, the chip
  reads "Suggest tags" and asks for tags only through the user's own AI. It is hidden for Know-N or with
  tags off.
- **Saved results.** `popup-result-suggestions` never offers a folder for a rule-owned result.

Tags-only requests stay foreground and user-authorized: only a save the user just made (popup, menu,
toolbar) runs one. Receipt replay never invokes a provider. Observed creates are AW-20.

### What the user sees

- **Manual popup (`src/popup-rule.ts`).**
  - Before Save, it asks the worker (`known.automation.match`, read-only) what a rule would do with the
    folder the save would otherwise use.
  - A placement shows the rule's folder on the pill with a muted "By rule" mark (fork icon). The
    tooltip names the rule.
  - Picking another folder removes the mark and makes the choice explicit.
  - Save sends the replaced folder, and the worker decides again.
  - After the save, the pill follows where the bookmark went. The status reads
    "Saved to Academic · Rule “arXiv papers”".
- **Automatic result panel.**
  - A placement adds the calm line "Saved to Academic by rule “arXiv papers”." and the "By rule" mark
    instead of "AI pick".
  - While the user's AI suggests tags, the line reads "Suggesting tags…".
- **Context menu.** The persisted feedback and action title read "Saved to Academic by rule “arXiv
  papers”.".
- **Save tabs.** A placed row ends with "Rule “arXiv papers”". A row whose rule could not act shows a
  "Rule didn’t apply" badge, with the reason as its tooltip.
- **A rule that matched but could not act** says so in the warning alert. This covers a blocked folder,
  an out-of-date copy and disagreeing rules:
  - "Rule “…” matched, but its folder isn’t in this browser, so the page stayed where you saved it."
  - The manual popup stays open 5 s instead of 1.5 s for it.
- **A kept explicit choice** is a calm note: "Kept the folder you chose; rule “…” didn’t move it."
- **Copy.** All lines come from one function, `automationSaveLine` in `src/save-status.ts`. Strings are
  in `en` and `zh_CN`. `docs/ui-design.md` records the mark and the line.

## Limitations

- **Not run in a real browser or against a server.** AC-01, AC-02 and AC-04 hold in unit tests over the
  real capture coordinator and store. They are not executed in Chromium with a live bundle. The
  observed star-button path and its real-browser run (AC-09, AC-49) are AW-20.
- **AC-04 "a local tag result marks the tags task satisfied on the receipt" cannot be met.** The
  receipt contract (`LocalReceiptInput.satisfiedTaskTypes`) accepts only `classify.root`, at most one
  item. The receipt therefore claims the rule's placement and nothing for tags. The tags the user's AI
  suggested or added stay local annotations. This is a contract gap for the backend lane; no server
  file was changed.
- **`hasTag` rules never match at intake.** Facts carry no tags, because tags are written after the
  create, exactly as the server sees a Sync create. A rule that needs tags applies only to later
  events.
- **Rules place only while this browser syncs the rule's collection.** With Sync stopped there is no
  canonical mapping to trust, so the save keeps its own folder and no receipt is written.
- **The popup preview is advisory.** If the bundle changes between opening the popup and Save, the
  worker's decision at save time wins, and the pill is corrected afterwards.
- **Storage.** The decision lives on the capture task (IndexedDB). Receipts are still in
  `chrome.storage.local` until AW-21.
- No backend or web files were changed.
