# AW-52 — automation plan approvals and effect-specific Undo

Built on AW-34 (`db0f7e3`) on `main`. Contract `0.2.1-design`; the six-state hand-off is
[fixtures/aw-25/statuses.json](fixtures/aw-25/statuses.json). The page reuses the existing Approvals queue
and the bookmark page's Automation section. It does not approve on its own, construct plans, infer policy,
or compute authorization.

## What shipped

### Recognizing automation plans in Approvals

- **Candidate.** An approval is an automation candidate when its `reason` is `automation:<ruleId>:<jobId>`,
  the note the server's automation plan builder writes.
- **Confirmation.** The reason is untrusted agent-visible text, so a candidate becomes an automation plan only
  when the Owner's own `GET /me/automations/jobs/:jobId` returns a job whose `planId` equals the approval's
  `planId`. Anything unconfirmed stays an ordinary agent plan, with its reason shown as untrusted text and the
  normal approval flow. That includes a forged reason, a superseded plan and a missing job.
- **Rule and run.** The rule's name and the job's run are read the same way. The plan's effect is the run's
  receipt with `kind: plan` and the same `planId`.

### How a confirmed automation plan shows

- An **Automation** badge, a plain title, **From rule** linking to the rule, and **Proposed by** with the
  agent's name. The plain title maps the server's three fixed automation summaries ("Add a note to a
  bookmark", "Change a bookmark's tags", "Move a bookmark") and shows any other summary verbatim.
- The raw `automation:…` reason is not shown. Operation rows label `create_annotation` and `update_node` in
  words, as they now do for every plan.

### Decisions

- **Approve / Deny** send `POST /me/automations/jobs/:jobId/decision` with `{decision, proposalDigest}`
  taken exactly from the job, plus a reason. `If-Match` is the job revision; CSRF and Known-Command-Id are as
  usual.
- The server checks both and records the decision in the existing Plan/Approval ledger. It applies an
  approval right away; the generic plan decision is not called for these plans.
- The queue re-reads afterwards. A stale digest or revision asks the Owner to review the latest version. An
  unknown outcome asks them to try again, with the same command id. Any other refusal is shown as the server
  worded it.

### Undo

- A committed automation change offers **Undo this change**, but only when the effect receipt says
  `undoAvailable`. It sends the effect id, its digest and the run revision to `POST /runs/:id/undo`.
- The generic version-restore Undo, and its "Approved by you" line, are not shown for automation plans.
  Restoring a collection version would overlay newer work, which AW-25 rules out.
- When Undo is not available, the receipt's reason is shown in plain words, for example "Can't undo here:
  tags, notes and grouped changes have no single-step undo." Nothing promises a field-level restore.

### Other states, filter and bookmark page

- **States.** A denied plan says nothing from that step was applied. A stale proposal says it can't be
  applied as it is. An expired plan whose job is in review offers **Propose again**, which sends
  `POST /jobs/:id/retry` with the job revision; the server decides whether the plan can be proposed again.
- **See the run** links each automation plan to its AW-34 run page.
- **Filter.** All / Automations · N / Agents · N appears once any automation plan is confirmed.
- **Bookmark page.** A plan effect ("Agent change") keeps its effect-specific Undo or reason and links
  **See the approved change** to `/approvals/:planId`. The run page shares the same component.

## Limitations and contract gaps

- **Recognition depends on the plan's reason.** Plans are recognized by their reason text, then confirmed by
  the Owner job read. A typed `automation: {ruleId, jobId}` field on `WriteApprovalView` would remove the
  parse and the extra reads. Confirmation is capped at 50 plans per page load, and the queue lists at most
  100.
- **A superseded plan reads as an agent plan.** After Propose again, the old expired plan no longer matches
  its job, so it shows as an ordinary agent plan, with its reason as untrusted text.
- **No tag-feedback controls.** The tag-rejection endpoint
  (`/rules/{ruleId}/rejected-tags/{tagKey}`) exists, but the Owner job view carries no accepted tag output, so
  this task doesn't render tag feedback.
- **Not run against a real backend.** No hosted or real-backend run was made. Server behaviour comes from
  AW-25's integration evidence.
- No backend files were changed.
