# AW-69 — extension: review browser rules against the account's rules

Built on AW-68 (`c1168c59`) on `main`. Design [01 §7.5](../design/01-architecture.md#75-browser-rules-adr-a24-au-34),
story AU-34; acceptance AC-71.

## What shipped

### The check (`src/automation/browser-overlap.ts`)

Each switched-on browser rule is compared with the account's rules in force here, through the shared evaluator.

- **Witness.** A page built only from the two rules' own values (their sites, paths and title words, merged)
  that both match proves they can file the same page. Tags never take part: they are written after the save.
- **Replay.** Both sets run over this browser's 2,000 most recently added bookmarks (`chrome.bookmarks.getRecent`);
  the count is how many real pages both take.
- **Labels.** *Duplicate*: some page is shared, the conditions are the same after normalization (group order
  ignored) and both file into the same folder here. *Conflict*: some page is shared and the folders differ,
  including an account folder that is not in this browser; the account's rule wins at save, so the browser rule
  never files those pages. Shared pages into the same folder with other conditions change nothing and are not
  reported. A row shows one account rule: a duplicate first, else the conflict with the most shared pages.
- **Limits stated in the code.** A scope folder on an account rule is not modelled, so an overlap may be
  narrower than reported; finding no witness proves nothing, which is why the replay count is the second signal.

### In the worker (`src/sw/automation.ts`, `src/sw/automation-browser.ts`)

`automationStateView` projects the bundle's rules to their folders here (the AW-49 projection) and passes them
to `browserRuleViews`, which adds `account` to each browser rule: kind, the account rule's name, sentence and
folder, the replay count, and whether the Owner already reviewed it. Paused or absent account rules, a
switched-off browser rule and a signed-out page have nothing to compare.

*Keep both* is remembered on the browser rule as `reviewed: [{ accountRuleId, key }]`, where the key is the
account rule's revision and binding revision, so a changed account rule is shown again
(`known.automation.browser.review`, Options only).

### On the page (`src/automation/browser-rules-pane.ts`)

- One warning notice in *Rules in this browser* while anything is unreviewed: "2 of your browser rules overlap
  your account's rules." with *Review*.
- Each row names the account rule it meets in a second line: "Your account's rule "arXiv papers" files these in
  Academic first. 37 of your bookmarks match both." (toned until reviewed), or "… does the same." Unreviewed
  rows carry *Overlaps* or *Same as account*.
- *Review* lists each open overlap with both rules side by side and the replay count. A conflict offers *Keep
  both* and *Use the account's* (switches the browser rule off); a duplicate offers *Remove mine* and *Keep
  mine*. Each choice is sent on its own and the item says what happened; nothing changes until the Owner
  chooses. *Add mine to the account* comes with AW-71.

Copy is in `en` and `zh_CN`.

  badge and line; the review sends *Keep both* with the revision key and *Remove mine*; *Use the account's*
  switches the rule off and stays open if that fails.

## Limitations

- No real-browser run in this packet: the comparison reads a bundle that only a server issues; the worker test
  uses a contract-valid bundle built by `ruleBundle` in `automation-fixture.ts`.
- Browser rules that disagree with each other are not reviewed here; at save they keep the page where it was
  saved and say so (AW-67).
