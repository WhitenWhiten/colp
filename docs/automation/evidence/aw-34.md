# AW-34 — web run history, waiting work, budgets and result states

Built on AW-12 (`979dd9e`) on `main`, against contract `0.2.1-design` and the generated
`packages/web/src/generated/automations-v1.ts`. Every count, state and eligibility shown comes from the
backend DTOs (Rule, Run, `AutomationRuleUsageView`, Job, DependencyReport, HealthReport). The browser does
not compute permission, retry safety, effective rule state, completion, or a sum of job states.

## What shipped

### Rule page — `/automations/rules/:ruleId`

- **Header and sentence.** The header shows the rule's name, its server state in plain words, and the actions
  that state allows: Pause with If-Match, or Preview and turn on, plus Edit. Below it is the rule sentence
  with current folder names.
- **Open health notices.** These come from `GET /rules/:id/health`, with the same repair links as the list.
  Check again sends the rule revision.
- **Work and allowance.** This panel renders `usage` as the server sends it:
  - the period and admitted runs;
  - one row per job state the server counted (waiting, ready, with an agent, saving, needs approval,
    outcome unknown, blocked, done). The rows are never added up;
  - "On hold", marked as also counted above;
  - "over the daily allowance", shown as a note on the blocked count;
  - today's allowance as `reservedRuns of dailyRunLimit` with `remainingRuns` and the UTC budget day. It
    says the server still checks every call. When it is exhausted, it says bookmarks are still filed;
  - agent calls and cost. `unknownDisclosed` reads "Your agent bills these; COLP can't see the amount", and
    `known` shows the reported micros as an exact decimal with no invented currency;
  - delivery capability.

  A rule without `usage` (M1 placement) says why there is nothing to count.
- **What it relies on.** Groups `GET /rules/:id/dependencies` by kind and role, names the destination folder,
  and shows the server's valid / warning / blocked status.
- **Runs.** Newest first, each linking to its run page. "No runs yet" reads as normal, not as a fault (AU-22.3).
  "Look further back" continues the scan (see limitations).

### Run page — `/automations/runs/:runId`

- **Title and explanation.** A short status headline for each of the eight run states, the state's meaning,
  and the server's explanation in plain words; unknown explanations are shown verbatim. A held run is marked
  separately from its state.
- **What it changed.** Each effect has Undo, which uses the shared effect list with the bookmark page. Undo
  appears only when the receipt says so; otherwise the reason is shown. After Undo the page shows the run the
  server returned.
- **Agent work.** Each job is read with `GET /jobs/:id`, up to 25 per run; the page says how many it left out.
  Each job shows its task, state and explanation, with the one action that state offers:
  - awaiting approval → link to Approvals;
  - outcome unknown → Try again (`POST /jobs/:id/retry` with the job revision). The server decides
    eligibility, and a refusal is shown as the server worded it;
  - other states → explanation only.

  A job that can't be read says so.
- **Cancel remaining work.** Offered for waiting, running, blocked and review runs, behind a confirm. It sends
  `POST /runs/:id/cancel` with the run revision. Completed effects stay.
- **Manual children.** Child runs are listed as links.

### Links and shared pieces

- Rule names on the Automations list open the rule page.
- Needs attention offers View on the disagreeing run.
- Bookmark history titles open their run.
- The bookmark section and the run page share `RunItem` and `RunEffects`.
- Client additions: `getRuleDependencies`, `getJob`, `retryJob`, `cancelRun`, and a run-list `limit`. They
  follow the same CSRF, Known-Command-Id and If-Match rules.

### States covered

| | Rendering |
| --- | --- |
| Loading | Route loading for the rule or run; "Loading agent work…"; inline "Checking…". |
| Empty | No runs, no effects, no agent work, and no usage for placement-only rules. |
| Error | Inline errors with Try again for runs and dependencies, and per unreadable job. |
| 404 | "This rule / run is not available". |
| 403 | The shared "You do not have access". |

## Limitations and contract gaps

- **No rule filter on runs.** `GET /runs` has no `ruleId` filter, so the rule page scans the account's run list:
  each look reads up to 5 pages of 100 or until 20 matches, and "Look further back" continues. A `ruleId` query
  on the runs list would remove the scan.
- **One usage period.** AU-23 asks for 7- and 30-day views, but `usage` exposes the server's single retained
  period. The page shows that period as given.
- **Jobs are read one at a time.** There is no job-list endpoint for owners, so each job is a separate read,
  capped at 25.
- **Runs don't link to their bookmark.** The Run DTO still carries no bookmark identity.
- **Cancel and Try again are offered by state; the server decides.** Cancel is offered for the four open states
  and Try again for `uncertain`. Both are refused server-side when ineligible, and the page shows the refusal.
- **`costDisplay` is not shown verbatim.** It is a technical sentence, so the page phrases the same
  `externalCosts` fact for the owner. `reportedCostMicros` has no currency in the contract, and none is shown.
- **Delivery is shown as unavailable.** Before AW-29 the capability is `unavailable`, and the page says agents
  poll.
- **Approvals has no automation filter yet.** The Approvals link opens the general queue; AW-52 adds the filter.
- **Untested against a real backend.** All runs used mocked APIs; no hosted or real-backend run was made.
- No backend files were changed.
