# AW-60 — extension: digest unread indicator and navigation

Built on AW-54 (`2b42346`) on `main`. Contract `0.2.1-design`, shared core `@know-n/colp` 0.2.0. It uses the
`RunPage` read model AW-54 reads (`unread`, `outputCount`, `kind`). Story AU-24; acceptance AC-48 (the
extension half).

## What shipped

### A projection, not a ledger (`src/automation/digest-indicator.ts`)

- **What counts.** The indicator is the runs the server reports as `unread` with `outputCount > 0`,
  from the last status read, newest first. It is worked out each time from that read, never stored
  as its own unread list.
- **What never happens.** Content is never fetched or counted, and the extension never calls the
  read marker (`POST …/runs/{id}/read`). The Owner reads the digest on the web run page, which marks
  through the output actually viewed (AC-66). The next status read then clears the indicator.
- **Wording.** The run list doesn't say which kind of text an output is (summary, review or digest),
  so the wording follows the run kind. Batch runs give "1 new digest"; otherwise "2 new results from
  your automations".
- **Navigation.** A single result opens its run (`<server>/automations/runs/<id>`); several open the
  web's Digests page (`<server>/automations/digests`).

### Toolbar badge (`src/action-badge.ts`, `src/sw/automation.ts`)

- **Shown.** The count, in `--accent` (`BADGE_ACCENT`), with the tooltip "1 new digest.". It is
  painted after each status read on the existing automation pass: the five-minute alarm, opening
  Options › Automations or the popup, and "Check now".
- **One answer, shown once.** The badge reflects the server's state at its last read; repaints are
  skipped while nothing changes.
- **Stale.** When the server can't be read, the badge keeps the last answer, turns `--muted`
  (`BADGE_MUTED`, pinned against the tokens), and the tooltip says when that answer was read: "1 new
  digest as of Oct 14, 8:00 AM. Your server couldn’t be reached since."
- **Two owners.** A save problem ("!") always wins the badge. Anything that clears it hands the
  badge back to the count instead of blanking it: a successful save, a granted bookmark permission,
  or an install or update.
- **Restarts.** The browser forgets action badges on restart, so the worker puts the last answer
  back at start.
- **Sign-out.** Signed out, the badge is cleared at the next pass.

### Popup line (`src/popup-digest.ts`)

- **Text.** "1 new digest from “Weekly reading digest” · Read", or "2 new digests · Open Digests". A
  stale answer adds "as of 3 hours ago". It appears in both the manual popup and the automatic
  result.
- **Priority.** It is the note line's last source, so anything about the page in front wins.
- **Freshness.** Asking for it nudges a due status read, so the badge catches up within the pass.

### Options › Automations

A run with an unread result shows a "New" badge (accent tokens) in place of its status. The web run
page is one click away, as in AW-54.

### Also

"Check now" pressed during a background pass now runs right after that pass. Before, it was folded
into the pass and could skip its read.

## Limitations

- **The badge in real Chromium was not run.** It needs a signed-in extension and a live server for
  the cookie read. The worker logic runs in unit tests against contract-valid DTOs; the popup and
  Options states were seen in xvfb screenshots with stubbed messages.
- **"Once" means the badge.** The count shows while the server says the result is unread and goes
  when it is read. There is no separate one-time notification.
- **Only the 20 newest runs are read.** An unread result older than those does not appear in the
  badge, though the web's Digests page still lists it.
- **Wording by run kind.** "Digest" versus "result" follows the run kind, because the run list
  doesn't name the output's text type and fetching outputs is out of bounds.
- No backend or web files were changed.
