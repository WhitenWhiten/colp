# AC-39 — s2 capacity and saving availability

Status: **failed; not release acceptance**. Production code baseline:
`f6beff6da08aa56d7980dd8ffc59ab9a46130021`. Measurements were made on s2 on
2026-10-14 UTC, with the existing COLP application and PostgreSQL stopped normally.
Their volumes were not modified. The test used a separate disposable PostgreSQL 16
container on loopback port 15439, independent credentials and isolated schemas.

## Environment and method

- 3 virtual CPUs, Intel Xeon E5-2697 v2, approximately 2 GiB RAM and 1 GiB swap;
  ext4 virtual disk. Node 22.23.2; PostgreSQL 16.
- No additional CPU or memory cgroup restriction. Test pool: 6 connections,
  5-second connection timeout, 5-second lock timeout, 15-second per-statement
  timeout. A separate one-connection observer samples the collection replica gate.
- The opt-in runner is `packages/server/tests/support/ac39-capacity.ts`.
  It calls production canonical mutation and Automation transactions through the
  existing fixtures. This is database/application capacity evidence, not an HTTP,
  reverse-proxy, browser, real Sync-client or full production-worker benchmark.
- Manual snapshots contain exactly the stated number of initial bookmarks, all
  requiring placement. Bulk seed rows preserve their canonical payload identity
  and position. Seed creation is not claimed as ingestion evidence. Measured
  movements and concurrent saves use production canonical transactions.
- Three independent save streams target the same collection, another collection
  of the same Owner, and another Owner. Each stream schedules 20 arrivals at
  5 requests/second; latency starts at scheduled arrival, including queue delay.
  This is a finite burst, not a sustained-capacity or tail-latency SLA estimate.
- Rule fixtures use production create and activation-store methods; they bypass
  repeated enable previews during setup. The measured preview and admission are
  the real application paths, and active activation counts are asserted.
- Slow-worker fixtures use real machine credentials, pairing, durable admission,
  claims and typed results, with deterministic output and an artificial delay.
- Every remote invocation runs under `xvfb-run`, with a process timeout. No model
  provider or hosted Events service is involved.

The candidate thresholds were fixed before measurements: no failed saves,
save p95 <= 1 second, maximum save latency <= 2 seconds, run-once <= 10 seconds.
These are acceptance targets for this experiment, not an existing product SLA.
Even without these numerical targets, losing save availability violates AC-39.

## Initial failure

At only **100 bookmarks**, run-once took **19.56 seconds** and issued **5,758
queries**. The observer saw the replica gate held for at least **19.46 seconds**.
All 100 intended placements committed, but **20/20 same-collection saves failed**
with lock or pool-acquisition timeouts. Another collection of the same Owner had
12/20 failures; the foreign Owner had 14/20. Both control streams shared the six
application connections, so their failures demonstrate pool starvation rather
than a cross-Owner collection lock.

The capture-enabled baseline had no save failures and p95 277 ms. The earlier
capture-disabled baseline had p95 1.41 seconds; its cold-order effect means these
two numbers must not be interpreted as capture improving performance.

A second 100-member iteration completed before the stop: run-once 15.36 seconds,
gate observed for at least 15.28 seconds, again 5,758 queries and 20/20 failed
same-collection saves. Each control group had 12/20 failures. Its baselines had
no errors (capture off/on p95 351/197 ms). This reproduces the failure after warmup.

After this result the manual phase was terminated explicitly (exit 143), before
increasing to 500/1,000 members. Larger manual sizes and the 1,001-member rejection
were not accepted on this host by this run. The runner now stops automatically
when saving fails. The stage-level interruption is not a passing test result.

The code holds the collection replica gate from configuration/member validation
through sequential child-run inserts, canonical placement, receipts and final
run loading in one transaction (`manual-run-store.ts`). The measured query count
and gate duration support investigating that path first. Atomicity and immutable
preview guarantees must be preserved when addressing it; increasing lock timeouts
or the connection pool alone does not establish save availability.

## Low-concurrency control with canonical seeding

The follow-up created all 100 bookmarks through the real canonical create path,
then issued only **one save per control group** after observing the run-once
gate. With six application connections this does not saturate the pool.

- Run-once: **12.89 seconds**, **5,757 queries**, 100 committed placements.
- Gate observed for at least **12.79 seconds**, at most one observed gate waiter.
- Same-collection save: **failed at 5.06 seconds**, explicitly due to lock timeout.
- Same-Owner other-collection save: succeeded in **310 ms**.
- Foreign-Owner save: succeeded in **529 ms**.
- The 20-request baselines had no errors (capture off/on p95 844/600 ms).

This isolates collection-lock blocking from the pool starvation of the larger
burst and reproduces it without bulk-insert seed rows. The runner recorded the
failure and stopped further manual load automatically (exit 1). Single-request
control timings are individual observations, not p95/p99 estimates.

## Rule-count scaling

Three measured iterations per size, with one new canonical bookmark before each
admission drain. Initial fixture history is drained in the first iteration;
subsequent iterations process the new input. The preview sample grows from 1 to
12 bookmarks across the sequence; this is not a 500-rule × 1,000-member combined
backend benchmark. SQL counts below are for preview.

| Active rules | Preview time, seconds | Preview queries | Admission drain, seconds |
| --- | --- | --- | --- |
| 1 | 0.156–0.205 | 45 | 0.161–0.191 |
| 50 | 1.309–3.505 | 1,221 | 1.918–3.169 |
| 200 | 10.195–11.534 | 4,821 | 8.818–10.257 |
| 500 | 20.609–23.349 | 12,021 | 14.749–19.533 |

The measured preview query count is `45 + 24 × (rules - 1)` in this fixture.
The 200/500-rule cases fail the candidate 10-second operation budget. This
substantiates the previously deferred binding/folder-resolution batching concern;
the 500-rule contract limit alone is not a performance guarantee. No concurrent
saving measurement is claimed for this particular stage.

## Stalled worker and finite recovery

With the worker initially idle, 50 real canonical saves plus the fixture's
initial task produced exactly 51 ready jobs. Admission drained in 19.36 seconds.
The worker then consumed one job at a time, with 100 ms artificial external delay,
using deterministic typed summaries. All 51 jobs reached `succeeded` in 59.13
seconds, and no job had duplicate effect receipts.

The 50-save burst had zero errors, p95 1.350 seconds and maximum 1.368 seconds.
Recovery correctness passed, but the stage failed the candidate 1-second save-p95
target. Input production and recovery were sequential phases; this does not
establish sustained overload capacity, fairness, or availability during draining.

## Evaluator boundaries

Both a shallow predicate and a valid predicate at depth 16 / 128 nodes completed
three rounds of 500 compiled rules × 1,000 facts. All **3,000,000 evaluations**
matched, with zero budget errors. Depth/node-over-limit inputs were rejected.
Shallow rounds took 35.29–37.78 seconds; boundary rounds 64.09–69.48 seconds.

This microbenchmark invokes each evaluator with its own facts normalization, as
the existing AW-44 load test does; it is not a throughput estimate for the
production multi-rule path that shares prepared facts. Per-rule success also
does not establish a total request CPU budget. Its synchronous loop cannot
sample the event-loop histogram: the initial runner's 0.000511 ms sentinel must
not be interpreted as measured event-loop latency (the follow-up emits null).

## Reproduction

Use a disposable database; do not point the runner at a deployment database.
The recorded s2 failure is reproducible from `e310f74` (the unchanged production
baseline plus the evidence runner). Later optimized commits have separate results.
Install the locked server dependencies and Node 22, then from `packages/server`:

```sh
export KNOWN_TEST_DATABASE_URL='postgres://USER:PASSWORD@127.0.0.1:15439/ac39'
export AC39_OUTPUT=/absolute/path/results.jsonl
AC39_STAGE=manual AC39_SIZES=100 AC39_ROUNDS=1 \
  timeout --kill-after=20s 600s xvfb-run -a node --import tsx tests/support/ac39-capacity.ts
AC39_STAGE=rules AC39_ROUNDS=3 \
  timeout --kill-after=20s 600s xvfb-run -a node --import tsx tests/support/ac39-capacity.ts
AC39_STAGE=queue \
  timeout --kill-after=20s 600s xvfb-run -a node --import tsx tests/support/ac39-capacity.ts
AC39_STAGE=evaluator AC39_ROUNDS=3 \
  timeout --kill-after=20s 600s xvfb-run -a node --import tsx tests/support/ac39-capacity.ts
AC39_STAGE=manual AC39_SIZES=100 AC39_ROUNDS=1 AC39_SAVE_COUNT=1 AC39_CANONICAL_SEED=1 \
  timeout --kill-after=20s 600s xvfb-run -a node --import tsx tests/support/ac39-capacity.ts
```

Exit 1 represents a recorded threshold/correctness failure; a timeout or signal
is separately recorded and never treated as success. `AC39_SAVE_COUNT=1` reduces
the manual concurrent burst to one save per control group for lock isolation.

## Evidence boundaries

Initial smoke attempts exposed runner setup defects (wrong database environment
variable, then missing copied payload identity/position). They were corrected
before the quoted result; none is presented as a product failure. Source
typecheck and runner lint were clean. A broader ad-hoc typecheck including test
fixtures reports existing fixture typing errors, so it is not claimed as passing.

Successful finite bursts alone cannot certify sustained queue bounds, retention
growth, a maximum supported rule/member combination, or the production HTTP
service's capacity. Those measurements remain necessary after the saving
availability failure is resolved. Do not mark AC-39 passed or raise defaults.
