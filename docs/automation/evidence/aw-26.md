# AW-26 — target profiles and authenticated worker pairing

Baseline `ac79c62`; design `0.2.1-design`. The monotonic migration `202610301300` introduces profiles, targets,
external executors and one-time pairings, based on the actual `202610301200` head; no Events tables are created.
Owner CRUD reuses Session/Origin/CSRF/ETag/command receipts. Separate catalogs imply no permission.
Each target establishes an external executor identity; unverified agent task capabilities stay empty,
and serverModel/browser executors are explicitly unavailable.

HTTP `/api/v1/automation-work/pairings/claim` in production composition reuses the existing MCP OAuth
verifier (including the account-key token exchange), the current account/credential/ancestor/server epochs
and the shared MCP rate limiter. Bootstrap only needs the automationWorker opt-in + automation:work,
not the manager scope. A grant lasts five minutes, is stored hashed, binds the Owner, target generation, profile
revision and the expected client/credential identity, and is consumed atomically once. A safe replay of the same command still checks
current authority; a new command replaying a consumed grant, a foreign identity, or an expired/old-configuration authorization are rejected.

The one-time code is not written into the ordinary command receipt: following the existing account-credential issuance convention, replaying
the Owner issuance returns code=null; the contract adjustment states this semantic, and a lost initial response needs a new grant.
The profile observation returned to the worker is a strict allowlist of token-free identity/digests/epochs only, and arbitrary actors/requests
are never serialized. The Owner target view also re-checks the credential, so revocation/expiry cannot stay active.

The OAuth shared binding does not support restricted work. Only a real independent child key's stable binding (including ancestors
and account epochs) assigned to exactly one target gets dedicated isolation; the currently pinned rule privacy
is also passed into authorization, so an old restricted job is not relaxed when the target later becomes standard. Polling readiness means
permission to poll, not a guarantee that a worker is deployed or scheduled. Events is only waiting/unavailable, and production readiness is not inferred
from a URL, an Owner toggle or the AW-02 experiment. The AW-53 contract fixtures are in fixtures/aw-26;
there active is polling only, and the reachability fixture states capability unavailable without faking a network probe.
