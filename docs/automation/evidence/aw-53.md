# AW-53 — Agents: automation opt-ins, worker pairing and connection guide

Built on AW-52 (`5e410ac`) on `main`, against contract `0.2.1-design`. Tests are driven by the AW-26
hand-off fixtures in [fixtures/aw-26/statuses.json](fixtures/aw-26/statuses.json). Guide text follows the
AW-32 worker reference ([agents.md](../agents.md)).

The page renders the server's `wakeReadiness` and `wakeReason`. It does not negotiate transport, validate
grants, compute readiness or decide authorization. Everything below appears only where the server answers
the automation pause read; a 404 hides all of it.

## What shipped

### Opt-ins on the agent's card

A connection profile is matched to its agent by `authorizedClientId`, which is the MCP client id the Agents
list uses as its agent id. The card gets an **Automations** block with three switches:

- **Use for automations** (`automationEnabled`);
- **Manage rules** (`automationManager`);
- **Do rule work** (`automationWorker`).

Each switch is its own choice, so turning one catalog on or off keeps the others and `standard` as they were.
A change is a `PUT` of the full profile with the profile revision, so `authorizedClientId` and
`credentialBindingId` are sent back unchanged. Turning automations or rule work off unpairs workers on the
server, so the page asks first when paired workers would be affected. Profiles whose agent is no longer
connected are listed under **Other automation connections**.

### Automation workers

Each target shows:

- its name and where it runs;
- the readiness badge: Not paired / Waiting for events / Ready / Blocked / Revoked;
- the server's reason in plain words. Known reasons are mapped; unknown ones, including the AW-26 BE-3/BE-4
  fixture reasons, are shown verbatim;
- how it learns about work. A selected events mode reads "Chosen, not active yet" until the server reports it
  active. Polling says the interval is the worker's own and COLP doesn't start it;
- its credential: shared, or its own;
- which rules it can serve.

Revoked workers are counted, not listed.

### Pairing

- **Pair** sends `POST /targets/:id/pairings` with the target revision.
- The grant appears once, as the environment settings the reference worker reads, with its expiry. It is held
  only in component memory: never in the URL, `localStorage`, `sessionStorage` or logs. It is cleared when
  dismissed, when it expires, or when the worker is revoked.
- A replayed command returns `code: null`, and the page asks for a new code.
- A refusal (404 when the agent's opt-ins don't allow rule work) says what to turn on.
- **Pair again**, behind a confirm, is offered for blocked workers.

### Worker actions and the add form

- Each worker can switch between checking for work and events with a target `PUT`. The events switch is only
  offered where the server says Events are enabled. Revoke is behind a confirm.
- **Add worker** asks for a name, where it runs, the agent, how it learns about work (events is disabled when
  the server has Events off), an optional check interval of 1–1440 minutes, and standard or restricted rules.
- When events is chosen on a non-public address (`http`, `localhost`, private or link-local IPs, `.local`,
  `.lan`, `.internal`, `.home.arpa`), the form shows a setup hint: hosted agents probably can't reach this
  address. Design 05 treats origin shape as a hint only; the server still decides readiness.

### Connection guide

A new **Automation worker** tab:

- a dedicated key with `automation:work`;
- the opt-ins on its agent card;
- adding and pairing a worker;
- the reference worker command, pointed at this server's origin;
- polling versus events: direct-public HTTPS versus local polling, and hosted-service plan or workspace
  eligibility. It states that COLP doesn't create hosted agents.

## Limitations and contract gaps

- **Profiles can't be created from the web.** `credentialBindingId` is a server-side digest of the worker's
  verified token: the account key binding, or the automation OAuth connection id. The Owner session can't read
  it, and no Owner endpoint or MCP tool reports it. The page therefore manages existing profiles, and the
  guide says a profile must be registered through the automation API. An endpoint that registers "this
  connected agent" from its agent id would close the gap.
- **Matching is by client id.** Profiles are matched to agent cards by `authorizedClientId` equal to the agent
  id. Unmatched profiles appear in the workers section.
- **Events are not verified for real.** Events readiness, reachability and subscriptions are shown only as the
  server reports them. No hosted, dot or Events run was made, matching the AW-26 note that active fixtures
  are polling only.
- **`eventsSupport` is not shown.** It is always `unknown` before AW-46, so it isn't surfaced yet.
- No backend files were changed.
