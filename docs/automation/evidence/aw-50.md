# AW-50 — extension: persist and sync canonical-only placement receipts

Built on AW-49 (`921a7ef`) on `main`. Contract `0.2.1-design`. The receipts go to AW-17's
`POST /api/v1/automation-device/intake-receipts`.

## What shipped

### Receipt records (`src/automation/receipt-sync.ts`)

- **What a receipt holds.** A `PlacementReceipt` records:
  - the account and replica scope (owner key, collection, replica, binding generation);
  - the path, pre-save or observed;
  - the pinned rule, rule revision, binding revision and bundle revision;
  - the canonical destination, and for an observed correction the canonical root it came from;
  - the rule's own `satisfies` declaration;
  - the page title and URL, for local display only;
  - the **native observation**: native id, the destination's native folder, when the move was seen.

  The record is written (`add`) before anything touches the network.
- **What the server receives.** `serializeReceipt` builds the server document from canonical fields only:
  - the device id and Sync lease generation;
  - the local receipt id;
  - the canonical create operation, plus the corrective move and `beforeFolder` when there is one;
  - `committedNode`;
  - the pinned revisions;
  - `inputDigest` and `resultDigests`, computed as the server computes them;
  - the rule's `satisfies` declaration.

  It validates the document against `LocalReceiptInput` and throws rather than send anything else. Native
  ids have no path into it.
- **Bounds.** Records are kept newest first. Settled ones age out after 30 days, and at most 300 are
  kept. Writes go through one worker-wide queue.

### Joining Sync (`src/automation/receipt-evidence.ts`)

- **Create.** A receipt joins its create once the engine's own create receipt shows the Push applied
  (`identityFromCreateReceipt`). The queued operation supplies the url, title, tags and parent the server
  digests.
- **Move.** An observed correction also needs the applied `move_node` of the same bookmark into the
  destination folder, staged after the observed move.
- **Folded move.** If the queue folded the move into the create (the create already names the
  destination), no move is needed.
- **Until then.** The receipt stays `local` and is retried with backoff.

### Delivery (`syncReceipts`, `src/sw/automation.ts`)

- **When it runs.** The worker pass that refreshes the bundle also sends due receipts. It runs on the
  same `known-automation` alarm and right after a receipt is recorded, with the Sync bearer and session.
  Each attempt is a new `Known-Command-Id`; the local receipt id is what makes a retry idempotent.
- **Answers.**
  - `waitingForSync`: retried with backoff, 30 s doubling to 1 h.
  - `accepted`, `review`, `rejected`: recorded as given.
  - `automation_command_conflict` or `invalid_request`: the receipt needs attention.
  - Transport failures, 401/403, 404, 429/503: retried.
- **Scoping.**
  - A receipt of another account is never read for sending.
  - Another collection waits.
  - A receipt from another replica or binding generation needs attention (`staleGeneration`); it is not
    re-associated.
  - Receipts older than seven days stop with `expired`.
  - Without the server device id (see AW-49), receipts wait.
- **No local claims.** Nothing is marked succeeded locally. Only the rule's `classify.root` is claimed,
  and the server decides it.

### Options › Automations: Recent placements

Each recent placement shows:

- its page title;
- the folder, the rule and when it happened;
- one badge while pending or wrong: "Waiting for sync", "Needs review", "Not accepted" or "Couldn't
  confirm".

A confirmed placement has no badge. The page re-reads when the receipts change. Strings are in `en` and
`zh_CN`.

`automation-receipt-sync.test.ts`:

- **Serialization.**
  - A pre-save receipt serializes to exactly the expected document, with the server's own golden
    `inputDigest`/`resultDigests`.
  - An observed receipt carries `placementOperationId`/`beforeFolder`. Its JSON contains neither native
    id nor the word "native".
  - An empty declaration claims nothing, and a receipt without canonical identity cannot be serialized.
- **Receipt before Sync.** Nothing is posted until the create is applied. The server's `waitingForSync`
  is retried later with the same receipt id, then accepted, and never sent again.
- **Sync before receipt.** Accepted on the first post.
- **Observed correction.** It waits for the move, then posts both operations. A folded create posts
  without a move.
- **Server answers.** `review` and `rejected` are recorded as given. Backoff grows on transport failures.
  A command conflict needs attention.
- **Scoping.** Accounts, collections and replica generations stay apart. A missing device id waits.
- **Restart.** A new store over the same storage finds and finishes the receipt.
- **Move evidence.** Only an applied move into the destination, made after the observation, is joined.

## Limitations

- No save path records receipts yet. Pre-save (AW-19) and observed create (AW-20) call
  `recordPlacementReceipt`.
- Storage is `chrome.storage.local`. AW-21 moves receipts and the bundle to the IndexedDB automation
  store and adds generation recovery.
- **URL digest.** The input digest uses the URL and title the extension pushed in its create. A server
  that rewrote them on ingest would answer `rejected`, and the page would show "Not accepted".
- **Device id.** It is read from the account's Sync status (see AW-49). Without a Product session,
  receipts wait.
- Not run against a live server or in a real browser; AW-17's integration evidence covers the server
  side.
- No backend or web files were changed.
