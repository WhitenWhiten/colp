# AW-31 — authenticated worker HTTP and MCP orchestration

Baseline `3bb4fd1`, contract `0.2.1-design`. Stopped after AW-31; AW-32 and later tasks were not started.
Per ADR-BE1 and the frozen catalog, seven manager and eight worker tools (fifteen in total) are mounted.
HTTP and MCP reuse the configuration, pairing, ready queue, input, lease and typed-result application services;
list/get/call keep using AW-30's current profile, scope, credential and pairing decisions.

The production API mounts the worker service when the Automation configuration/runtime and MCP Write composition are available
(now `KNOWN_FEATURE_AUTOMATION_WORK`), and the outbox worker enables task admission/scheduling as well. Deterministic intake runs first and
does not consume optional budget; when each task first becomes ready it pins the allowlisted inputs, revisions, the declared accepted predecessor
results and the input digest. Migration `202610301400_automation_worker_input_pins.ts` protects these pins in the database.
Only tasks on the same source are advanced serially, without rewriting the declared DAG; later canonical revisions come from the effect
receipt, and a manual edit invalidates the old input. Every ready job has a ledger deliveryHandle, without needing Events.

The claim token never enters the durable command receipt; replaying a claim requires reconciliation and does not re-issue the secret.
Replaying a heartbeat re-checks the current lease; submit recovers through the pinned proposal/plan/command identity.
An expired lease becomes uncertain; the Owner can explicitly retry only when there is no durable proposal, the input is unchanged and the pinned
maxCalls has headroom; the unknown-cost count is kept and the claim generation increases. The Owner HTTP decision
requires the current ETag and the exact proposal digest, reusing the existing Plan/Approval ledger. Before the canonical commit
the current worker, target, input and subtree authority are checked again.

Job gains the resultId/proposalDigest/planId and explanation needed for Owner approval; TaskInput gains the
declared DAG predecessor results. The adjustments are registered in `contract-adjustments.json` and synced to the Node schema/types, server
vendor, OpenAPI and MCP descriptors. An input lacking the readableText/metadata/folderDefinitions
capability is explicitly blocked, without implicit fetching or model calls. `AUTOMATION_SERVER_DAILY_RUN_CAP` defaults to 1000.
