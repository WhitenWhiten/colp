# AW-49 — extension: install the bounded bundle and project canonical bindings

Built on `5c40d71` on `main`. Contract `0.2.1-design`, profile `browser-bounded-v1`. The extension now
pins the published `@know-n/colp` **0.2.0** (exact) and uses its `automation` subpath. It does not copy
the evaluator. Bundles come from the AW-18 device route; the fixtures follow
[device-bundle-cases.json](fixtures/device-bundle-cases.json).

## What shipped

### The shared core under MV3

The core validates with Ajv, which compiles schemas into functions at runtime. MV3's CSP forbids that,
and the release verifier rejects `new Function`.

- `scripts/generate-automation-validators.mjs` captures the exact schema objects and Ajv options the
  installed core compiles. It writes standalone validators to `src/generated/automation-validators.js`.
- The build plugin `scripts/automation-ajv-plugin.mjs` resolves `ajv/dist/2020.js` and `ajv-formats` to
  shims, and only for imports from inside `@know-n/colp/dist/automation`. Every other Ajv import is
  unchanged.
- The shim's `compile` returns the pre-generated validator for the requested `$defs` name. A name it was
  not generated for throws `automation_validator_unavailable` (fail closed).
- `build.mjs` runs the generator with `--check`, so a core upgrade with a changed schema fails the build
  until the validators are regenerated.

### Bundle installation (`src/automation/runtime-profile.ts`, `bundle-store.ts`)

- **Checks.** A bundle is accepted only when all of these hold:
  - it passes the `RuleBundle` schema;
  - its profile is `browser-bounded-v1`;
  - its digest matches `automationDigest` of its content;
  - it has not expired;
  - a paused snapshot carries no rules, and rule ids are unique;
  - every rule passes `validateM1Rule`, declares intake, has folder-only bindings, and its
    `semanticDigest` equals `ruleSemanticDigest(definition)`;
  - all its folders name a single server.

  Only the complete `definition` is evaluated. `programId` and `parameters` are never read.
- **Rejected bundles.** Any failure rejects the whole bundle. The previous valid bundle stays in force and
  the reason is recorded.
- **Ordering.** Ordering uses the monotonic `settingsRevision`; bundle revisions stay opaque.
  - An older sequence is refused even while it has not expired.
  - An equal sequence may refresh expiry but never lift a pause. A learned pause holds until a newer
    sequence arrives.
- **Storage.** The record is one value replaced in one write, behind a single worker-wide queue. It is
  keyed by server origin and account, so another account never reads it.

### Binding projection (`src/automation/binding-projector.ts`)

- A rule folder (`serverUuid`, `collectionId`, `nodeId`) resolves to a native folder only through the
  current Sync scope's mapping and a live native lookup.
- Another collection, a missing mapping, a deleted native node or a non-folder each leave it
  **unresolved**. Nothing is looked up by title or path.
- The reverse walk (native parent → canonical parent and ancestors) stops at the first unmapped folder.
  It mirrors the server's `ancestorIds`, so scope rules see the same facts.

`evaluateLocalRules` reproduces the server's `evaluateRuleEvents` around the same core calls:

- source and trigger eligibility, and scope folder;
- `compilePredicate` on prepared input;
- intake-role availability (`intakeRoleKeys`);
- one `arbitratePlacement` with the caller's intent.

AW-19 and AW-20 use it.

### Refresh (`src/sw/automation.ts`)

- **When.** A new `known-automation` alarm runs every 5 minutes, the pause bound the pages promise. The
  worker also refreshes at boot, when Options asks, and on **Check now**. Automatic attempts are spaced
  at least a minute apart.
- **How.** It reuses the Sync bearer and session (`pushSessionAuthority`) for
  `GET /api/v1/automation-device/bundle`, then installs the bundle. A failure records `offline`,
  `signedOut`, `unavailable` (404), `rateLimited` or `server` and leaves the installed bundle alone.
- **Acknowledgement.** After each install or rejection the worker posts `applied` or `rejected` with a
  diagnostic. The acknowledgement is advisory.
- **Pause details.** For a paused bundle, `GET /api/v1/me/automations/pause` (Product session) supplies
  `pausedAt` and `pausedBy` for the page.

### Options › Automations (`#automations`)

A Library page after Sync, built only from kit rows and lists:

- **Header.** "Open Automations" links to `<server>/automations`.
- **On this browser.**
  - **Status:** On · N rules, Paused (with who and when), Out of date (AU-10: "Rules are out of date;
    connect to refresh"), or Not set up.
  - **Rule updates:** when the copy was last updated, the 5-minute check, and the offline exposure
    window. "Offline, it keeps using its copy until …, and a pause you make on the web reaches it at the
    next check."
  - **Check now.**
- **Rules.** Each rule with "Files into <folder>". A rule whose folder isn't mapped here shows "Waiting".
- **Other states.** A rejected bundle shows a warning notice. Signed-out users get a sign-in card. A
  server without automations shows only the status row. All copy is localized in `en` and `zh_CN`.

## Limitations and contract gaps

- **Device id.** `BundleAckInput.deviceId` (and AW-50's receipts) must equal the server's replica
  `device_id`. Neither the Sync session nor the bundle returns it. The worker reads it from the owner's
  `GET /api/v1/sync/status` (Product session), matching its own replica id, and caches it per account
  and replica. Without that session the acknowledgement is skipped; nothing is guessed. Returning
  `deviceId` from the device routes (for example on the bundle response) would remove the extra read.
- **Server-side bundle revisions.** Every bundle `GET` issues and stores a new server revision. The
  5-minute refresh therefore writes one `automation_device_bundles` row per device per refresh.
- **Storage.** Bundle state lives in `chrome.storage.local`, which survives worker and browser restarts.
  The move to the IndexedDB automation store is AW-21.
- **No real Chrome or server run.** The refresh path's HTTP calls are not exercised against a running
  server here. The device routes' behaviour comes from AW-17/AW-18's integration evidence.
- No backend or web files were changed.
