# AW-20 — extension: observed creates (star button) and echo suppression

Built on AW-19 (`635ca19`) on `main`. Contract `0.2.1-design`, profile `browser-bounded-v1`, shared core
`@know-n/colp` 0.2.0, M1 rule fixture
([m1-placement.json](../../../packages/extension/tests/fixtures/automation/m1-placement.json)). Stories AU-07,
AU-08 and AU-11; acceptance AC-09, AC-49 and AC-12.

## What shipped

### Why a bookmark appeared (`src/automation/causation.ts`)

Every bookmark created outside the extension's own saves is classified from evidence the extension
already keeps:

| Cause | Evidence | Intake |
| --- | --- | --- |
| `localIntent` | Sync captured a local create for it, with no reserved save | yes |
| `ownEcho` | the local create carries the extension's reserved placement (a Know-N save; AW-19 already decided) | no |
| `inboundProjection` | no local create, and a canonical (server) mapping names it: Sync applied it from the server | no |
| `import` | the browser's import was running (`onImportBegan`/`onImportEnded`, plus 5 s of grace), or a Know-N import plan is running | no |
| `recovery` | the same URL was removed in this browser in the last 10 minutes (undo, restore, re-creation) | no |
| `outsideCollection` | Sync did not capture it (unsynced or private folder): there is no canonical create to receipt | no |

Advanced bootstrap captures, subscription folders and creates during a recovery freeze never reach
this path.

**Projections and echo suppression.**

- A server projection is recognized by its canonical identity (the mapping the pull applier writes)
  and never starts intake. Two browsers projecting one change therefore never run a rule twice
  (AU-11).
- Only creates are observed. The rule's own move, and any later move or projection of it, is never
  re-evaluated: same-stage re-entry is denied.
- A server automation's later move reaches the browser as an ordinary projection, so the next stage
  continues on the server.

### Settle, check, move once (`src/automation/observed-create.ts`, `src/sw/automation-observed.ts`)

1. **Note it.** The worker notes the creation in session storage, but only for an account with rules
   in force. It hooks `sw/bookmarks.ts` after the Sync capture of the create. Removals are remembered
   for `recovery`.
2. **Settle.** After 3 s the creation is judged. The observation is taken out of storage first, so a
   worker that dies mid-way never repeats a move. An observation older than 60 s (a worker that slept)
   is dropped. The automation alarm also settles anything due.
3. **ADR-A17.** The bookmark must still be directly in a browser root: Bookmarks bar, Other bookmarks
   or Mobile bookmarks, by `folderType` with legacy ids 1–3 as a fallback; never managed. A folder
   picked in the star dialog, or a bookmark added inside a folder, is the Owner's choice and is kept.
   A root is a heuristic, not proof of no choice, hence the next three steps.
4. **Gone or edited.** A bookmark removed or reused since it was noted, or whose URL changed, is left
   alone.
5. **Decide.** The cause must be `localIntent`. The rules are then evaluated with AW-19's
   `decidePreSave` (same facts, `userDefault` intent).
6. **Re-check.** Right before the move, the bookmark is read again. If the Owner moved or edited it
   meanwhile, it stays.
7. **Move.** One native move into the rule's folder. Sync stages it like any user move.
8. **Receipt.** An AW-50 `observed` receipt records:
   - the rule, binding and bundle revisions;
   - the canonical destination;
   - `beforeFolder`, the root's canonical ref;
   - the native ids and the time of the move.

   AW-50 joins it to the create and that move, and sends both operation ids.
9. **One notice.**
   - "Moved “Attention Is All You Need” to Academic by rule “arXiv papers”."
   - It goes to the toolbar tooltip and the popup's note line (the existing save feedback,
     5-minute life), and as a toast on a visible Know-N page (`known.automation.notice`).
   - A rule that matched but could not act gets AW-19's line ("…so the page stayed where you saved
     it") and no move.

No model is ever asked on this path. It runs without the user's foreground gesture.

Chrome's star button itself cannot be driven by Playwright (it is browser UI). The spec creates
bookmarks through `chrome.bookmarks` from an extension page. That raises the same `onCreated` event
without a reserved Know-N save, which is exactly the signal the star dialog produces.

## Limitations

- **The server half of AC-09 was not run.** "The server records one intake covering create and move"
  needs a live server; the receipt sent is the AW-50 document AW-17 accepts. AC-12 with two real
  browsers is covered here by one browser's projection path only.
- **Synced range only.** A star into a root outside the synced range (mounted-folder Sync) is not
  intake: Sync has no canonical create for a receipt to name. Whole-profile Sync covers the roots.
- **Recovery is a heuristic.** A page re-created within 10 minutes of its removal is treated as an
  undo or restore and left where it is, even if the Owner meant a fresh save.
- **Import windows rely on the browser's events.** Where `onImportBegan`/`onImportEnded` are missing,
  a browser import into a root would be judged like new stars. Know-N's own import is always
  recognized.
- **Session storage.** Observations and the removal memory live in session storage and do not
  survive a browser restart. An observation not judged within 60 s is dropped, never acted on late.
  AW-21 moves the automation state to IndexedDB.
- **The notice only reaches extension surfaces.** It is the toolbar tooltip, the popup's next opening
  and a visible Know-N page. The extension has no notification permission or page scripts, and this
  task adds neither.
- No backend or web files were changed.
