# AW-45 — web Digests and paginated run-level text output

Built on AW-53 (`c549fb9`) on `main`. Contract `0.2.1-design`. Tests are driven by the AW-58 consumer
fixture, [fixtures/aw-58/handoff.json](fixtures/aw-58/handoff.json). Output text and read state come only
from `GET /runs/:id/outputs`, `POST /runs/:id/read` and the Run's `unread` and `outputCount` fields. No
webhook or event delivery is used as a data source, and nothing counts or groups bookmarks.

## What shipped

### What it wrote (run page)

A **What it wrote** section appears on the run page whenever `outputCount > 0`, above "What it changed".

- **Order and paging.** Outputs come oldest first, as the server orders them, with **Show more** following
  the opaque cursor.
- **Text is inert.** Each output's text is a React text node with `white-space: pre-wrap`, never markup. The
  test feeds an `<img onerror>` string and finds no element.
- **Provenance.** Each output shows its type (Digest / Review / Summary), "Written by" the worker (target name
  from `GET /targets`, or "a worker"), a link to the step that wrote it (`#job-<jobId>`, now an anchor on each
  job row), and its evidence: kind, reference and when it was observed.
- **Unavailable source.** A 404 for the outputs (source bookmarks gone) says the text isn't shown. No text is
  rendered, and nothing is marked read.
- **Mark read.** Through the last output on screen: `throughOutputId` is the last output displayed, sent with
  the run revision. Loading the next page marks through its last output. A later output that arrives
  meanwhile stays unread.
- **When a later output arrives.** It changes the run revision, so the mark is refused as stale. The page then
  re-reads the run and marks through the same output with the new revision, at most once per output and
  revision.
- **"New" badge.** It reflects the server's `unread` and stays for the current visit after the read is
  recorded. A refresh shows the server's state.

### Digests page — `/automations/digests`

Linked from the Automations header.

- **Which runs.** Runs with `outputCount > 0`, newest first, scanned from the run list (see limitations).
- **Each entry.** The rule name, the server's unread state ("New", with read entries visually quieter), the
  date, the run kind, and how many texts it has. The first 10 entries show a three-line excerpt of their first
  digest, or else their first text, read with `limit=3`.
- **Opening.** An entry opens `/automations/runs/:id#outputs`. The list itself never marks anything read.
- **Edge states.** Empty, loading, unavailable and error states are covered.

### Client

`listRunOutputs(runId, {cursor, limit})` and `markRunRead(runId, throughOutputId, revision)`, using the same
CSRF, command-id and If-Match conventions as the other automation commands.

## Limitations and contract gaps

- **No output filter on the run list.** `GET /runs` can't filter by output, so Digests scans the run list:
  each look reads up to 5 pages of 100 or until 20 matches, and "Look further back" continues. An output or
  unread filter would replace the scan and allow a reliable unread count. The page shows no count for that
  reason.
- **Read state is per run, not per output.** Outputs carry no read flag, only the run-level `unread`. The page
  shows "New" for the run, not for each output.
- **Withheld outputs are invisible.** When only some of a run's jobs read a deleted bookmark, the server omits
  those outputs, and the page can't tell they existed.
- **No real backend or hosted run.** Server behaviour comes from AW-58's integration evidence.
- No backend files were changed.
