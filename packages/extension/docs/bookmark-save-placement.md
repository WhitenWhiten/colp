# Bookmark save placement

`bookmarkInsertPosition` is `top` or `bottom` (default `bottom`). Creation initially places bookmarks relative to **all native direct children**, including folders and local-only nodes. `foldersFirst` defaults to `false`, so installing the extension or granting bookmark access never reorders the user's bookmarks. Turned on, it also groups native browser bookmarks: folders precede bookmarks, preserving relative order within each group. With both options enabled, a top bookmark ends up at the start of the bookmark group. The worker applies grouping to existing writable folders on startup, permission grant and preference changes, and to affected parents after creation, moves and native reorders. Managed/unsupported roots and subscription contents are excluded; protected siblings and separators anchor independent sortable runs. These native moves use ordinary bookmark event capture and therefore reach synchronized collections. Turning the option off stops grouping; it does not restore the previous order. Search keeps Chrome's search order.

The Product resource is `GET/PATCH /api/v1/me/bookmark-preferences`. PATCH uses the browser session, CSRF, `If-Match`, and `Known-Command-Id`. A missing database row reads as revision `0`. Concurrent writes cannot overwrite a newer revision; successful commands can be replayed with the same identity and request.

## One-click organization

Saving → Where bookmarks go → Organize existing bookmarks sits directly below Show folders before bookmarks. Organize opens the shared manager dialog with every writable browser root path and first-level folder selected. Root selections organize direct children only; first-level folder selections recursively organize all writable descendants. Deeper folders cannot be selected independently, including through a forged worker request. Root and folder selections are independent: organizing the root can move an unchecked first-level folder among its siblings, while leaving that folder's contents untouched. Managed/unsupported roots and subscription content are excluded.

Applying organizes only the selected scope for this operation and does not change the automatic sorting preference. Manual moves do not trigger a wider automatic sorting pass. The sorter moves each folder that follows a bookmark exactly once, which is the minimum when only folders may move and both groups retain their relative order. Already grouped contents need zero moves. The panel reports completed moves, including partial failures, and a retry does not repeat completed moves. Permission, sync recovery and live ancestry are checked before writing. The UI uses the existing `capture-dialog`, manager batch list, `check-row` and button recipes without additional CSS.

The extension cache is isolated by server origin and the verified credential subject (`Better Auth user.id`). The backend maps that identity to its internal account; the extension does not use an internal account UUID as a Product identity. Signed-out device preferences have a separate scope. Signing in does not upload the device values over account preferences.

Queued preference requests retain their origin, subject, and authority generation from admission. Account changes, sign-out, or reauthentication invalidate them before execution, cache writes, and response delivery; an old request cannot become a new account's edit.

Cookie-authenticated preference GET responses carry `Known-Bookmark-Session`, the public ID of the session used for that same read. The client requires it to match the session returned alongside the verified Better Auth user. A changed or missing binding leaves the local cache intact; it cannot cache another account's values after a website cookie switch. Deploy the backend header before the updated extension. The response body, preference ETag, and mutation receipts retain their existing contracts.

Offline changes retain the base revision and command identity. On reconnect they are conditionally uploaded. A 412 preserves both local and remote values and requires an explicit choice in Options; ordinary reads or edits do not silently resolve the conflict. Native saving reads the local effective preference and does not wait for a preference API request. Local preference messages bypass the Product request queue and do not persist defaults on a cache miss. Popup initializes from that local value before saving, then refreshes from Product in the background.

Options submits only the field the user changed. The worker merges that edit with the bound account's current cached values after earlier refreshes finish, so editing during initial loading does not overwrite an untouched preference with an uninitialized control value.

## Pinned bookmarks

A folder takes pins when New bookmarks go is Top of folder, Show folders before bookmarks is on, and the folder is organized: no folder after a bookmark, and no read-only, subscription or separator item among its bookmarks. All three are checked per browser, because both preferences are device values. Its children then read `[folders][pinned bookmarks][other bookmarks]`, each group in its own native order.

- **Flag.** A pin is a flag in the annotation store next to tags and notes (`pinned`, with a `pinSync` field on the shared metadata lifecycle). Native order stays the only order. `src/bookmark-pin-order.ts` holds the eligibility rules and the planners; `src/sw/bookmark-pins.ts` handles the `known.bookmarks.pin.status` and `known.bookmarks.pin.set` messages.
- **Pin.** This is refused with the missing conditions where the folder does not take pins. Otherwise the flag is written, then the bookmark moves to the end of the pinned section. Every move goes upward, so Chrome's same-parent index rules never come into play.
- **Unpin.** This is always allowed, including in a folder that cannot take pins. The bookmark follows New bookmarks go: the top of the other bookmarks, or the end of the folder.
- **Saving.** A new bookmark is unpinned and goes to the top or bottom of the other bookmarks. A Top save lands after the pinned section. The popup's pin toggle sends `annotation.pinned` with `known.capture.start`. The worker records the pin after the native create and places the bookmark at the end of the pinned section. A folder that cannot take pins saves the bookmark unpinned.
- **Moving.** A bookmark moved to another folder keeps its pin. That folder's pass places it at the end of its pinned section, if the folder takes pins.
- **Paused pins.** Where a folder stops taking pins (a preference changed, or a folder landed among the bookmarks), its pins are kept, synced and shown muted, but not enforced. They apply again as soon as the conditions return.
- **Order passes.** The folders-first pass and Organize run the pin pass after grouping folders. Both defer while the sync engine owns the native order, with the same 30-second retry as folders-first. A pin or unpin made then writes the flag immediately and leaves placement to that deferred pass.
- **Manager (#bookmarks).** A pinned row keeps an ink pin in view. A paused pin is muted. Elsewhere, the pin action appears on hover and in the row menu. Where pins are off, the action is `aria-disabled` and opens a dialog that lists each condition with its state, plus a link to Saving. Drag-and-drop keeps each group inside itself. Dropping a pinned row on the first other bookmark puts it at the end of the pinned section.
- **Popup.** The pin toggle sits at the end of the Folder row and follows the chosen folder, including AI picks. Where pins are off, it explains the missing conditions in one line under the folder. Editing an already-saved bookmark, and the automatic-capture result panel, show the saved bookmark's pin and apply a change on Done, after any move. A pin pressed there but not yet applied drops if the folder stops taking pins (for example, after the AI moves the bookmark); a saved pin stays and shows paused.
- **Sync.** The pin travels as the Node extension `https://known.example/extensions/bookmark-pin-v1` = `{ "pinned": true }`; absence means unpinned. The backend accepts that namespace only on bookmarks and only with exactly that value. Because the value is two-state, the whole-map `extensions` merge can never conflict three ways, and a pin on either side wins at first sync. Order still syncs only through sibling anchors. A receiving browser places pins with its own passes, and only where its own preferences allow.
- **Web.** Product read views (editor page and public collection) carry `pinned: true`, and public snapshots allow the pin namespace. Library and public pages show the owner's pins. Web cannot pin or unpin. Reordering a folder layer never moves an other bookmark above a pinned one, and a toast explains that pins are set in the extension.

## Native creation

Popup, classification confirmation, page/window worker entries, shortcuts, and manager bookmark creation use the shared placement/save path. The default target and effective position are fixed for a save. Popup's override belongs to that save and does not change the account default; a later preference response cannot replace a choice the user has touched.

A top batch `[N1, N2]` creates `[N1, N2, existing…]`, using one initial native children read and a serial cursor. Bottom appends in input order. A confirmed partial prefix is retained when the worker resumes. Resume reads the original folder again and inserts after the confirmed prefix's current position, preserving input order when other siblings were inserted or removed. A missing, moved, or reordered prefix requires location review. The session record also retains the entry kind, collection, original parent, and effective position; changes to the default position or remembered folder do not retarget a pending batch. A different collection or a removed sync boundary cannot resume it. Folder creation does not use the bookmark placement preference. Favicon failure cannot undo or reposition a created bookmark.

For a save associated with a sync collection, the shared path persists a placement reservation before `chrome.bookmarks.create`, then binds the returned native ID. An early `onCreated` event can match the reservation by its parent/content/index evidence. The reservation is completed only after the event has been durably staged. Completion first persists a separate receipt containing the confirmed native ID, then removes the reservation. If the native create result is lost, the save runner uses this receipt to resume the same node even after event consumption; a same-URL sibling is not a substitute. Receipts share the reservation’s 24-hour retention limit and are excluded from new event matching. Missing identity evidence or a subsequently deleted native node requires attention rather than automatic recreation. Ambiguous evidence enters attention rather than inventing an identity.

## Synchronization and recovery

The original native placement is encoded through existing COLP sibling anchors. The server does not reapply device preferences. A receiving browser with folders-first enabled groups its native order after Pull finishes and captures any resulting moves normally. When some siblings are excluded from synchronization, only the synchronized subsequence is expected to match.

An unknown Push outcome is replayed with the same operation bytes before considering a changed placement. After a definitive stale-position refusal, Pull refreshes the local projection; the retry reads real native children and verifies their authoritative mappings before selecting a new top/bottom anchor. Later batch items anchor after their confirmed predecessor. The retry gets a new legal transport idempotency key while retaining the operation identity.

If the original parent was deleted, a save with a placement intent is parked with `create_placement_parent_deleted`. It must not silently become a successful append in a different recovery folder. Incomplete position evidence similarly parks with `create_placement_unproven`. Both states survive engine wakes and show that the save location needs review. Legacy native creates without this save intent retain their existing recovery behavior.

A batch predecessor that has been deleted or moved out of the original folder is unproven, not an upload still waiting to finish. A predecessor with a provisional identity can defer twice after the first stale refusal; the third recovery attempt parks with `create_placement_unproven` if its identity remains provisional.
