# Protocol Corrections

## 2026-07-17 - CORE-0029 Privacy-safe profile ID derivation

**Original problem:** CORE-0029 recommended a random identifier or server-keyed HMAC and prohibited a raw hash of a low-entropy local identifier, while the adjacent sentence required `profileId` to be an irreversible hash and the canonical examples used hash-like local labels. The text also did not state that a random value is allocated once and persisted, or define the separation and encoding properties needed for independently interoperable HMAC derivation. Following the adjacent sentence could therefore violate the registered requirement, and independently chosen concatenation or key-rotation conventions could correlate profiles or produce incompatible identifiers.

**Why implementation-only was insufficient:** Package-local helpers could avoid raw SHA-256, but they could not resolve contradictory canonical guidance or make the wire examples safe to imitate. Random identifiers regenerated for every synchronization would not remain useful as profile identifiers, while unframed or unscoped HMAC inputs could collide across field boundaries, servers, or tenants.

**Exact protocol documentation and example changes:** `docs/01-core-data-model.md` now prohibits uploading either the raw operating-system path or raw local Profile identifier without requiring every safe identifier to be a hash. It requires the random form to use a CSPRNG once and remain persisted with the local Profile. The HMAC form includes server and tenant separation, a public key-version label, and unambiguous deterministic input encoding; server key material is not sent to clients or logs, and rotation uses a controlled version-to-key mapping. The canonical Source Reference examples now use a wire-valid `prf.r1.<base64url>` random identifier instead of hash-like local labels. The package format is `prf.r1.<32-byte-base64url>` for random values and `prf.h1.<keyVersion>.<HMAC-SHA-256-base64url>` for server derivation. Its HMAC transcript uses ordered unsigned 32-bit byte-length-prefixed context, key-version, server-scope, tenant-scope, and local-ID fields, plus a distinct string/byte tag; strings are NFC-normalized UTF-8 and byte identifiers remain exact.

**Compatibility and migration:** Both formats satisfy the existing 1-128-character opaque Wire ID grammar. Previously safe opaque profile IDs remain schema-valid because CORE-0029 is advisory and the shared `opaqueId` schema is not narrowed. Producers exposing raw paths, raw local identifiers, or their unkeyed low-entropy hashes should allocate and persist a random value or migrate server-side mappings to a versioned HMAC value. Rotation changes the HMAC-form identifier when its public key version changes, so servers must retain the controlled old-version mapping for as long as stored identifiers need resolution.

**Tests:** Evidence `core.privacy-safe-profile-id` covers exact 256-bit injectable entropy, malformed providers, wire bounds, independent HMAC transcript computation, key/version/server/tenant/local separation, concatenation ambiguity, NFC and malformed UTF-16, string-versus-byte tagging, key and input bounds, caller-buffer immutability, absence of raw-hash APIs and outputs, and the public root, server, and adapter surfaces. The package framing is pinned by the documented fixed vector `prf.h1.v1.jPlng8qXDyjhW30apPwPrim8J_5t5gH19VvKFe5KE4U`; this is a package/compatible-SDK contract rather than a requirement that deployments with independent keys produce equal opaque IDs. Protocol, schema, canonical-example, type, package, Registry, empty-evidence, and generated traceability checks cover synchronized assets. Newly explicit BCP14 details are registered separately and remain unverified rather than being accepted under CORE-0029.

## 2026-07-17 - CORE-0027 Snapshot-derived index projection

**Original problem:** CORE-0027 allowed a Snapshot to provide a derived `index`, while the canonical closed Node Schema rejected `index` everywhere. The protocol also left the field's wire type, Root representation, sibling scope, pagination behavior, and relationship to authoritative Sync state unspecified. A producer therefore could not emit the permitted hint in a Schema-valid Snapshot, and independent implementations could derive incompatible values.

**Why implementation-only was insufficient:** Package-local acceptance or derivation could not make a field rejected by the canonical wire Schema interoperable. Adding `index` to authoritative `$defs.node` would have made the hint available in Node writes and other state-bearing contracts, contradicting the requirement that Sync not depend on it. The shared protocol needed a Snapshot-only representation and common derivation rules.

**Exact protocol documentation and Schema changes:** `docs/01-core-data-model.md` now defines `index` as an optional I-JSON-safe, zero-based integer for a represented non-Root Node, derived among Nodes with the same `parentId` by unsigned ASCII-octet `position` order. Root omits the field or uses `null`. Numbering applies to the assembled logical Snapshot projection, does not reset at page boundaries, and numbers only represented siblings in cropped or sparse projections; a producer omits the hint when it cannot determine that projection. Received values are display hints only and must not be required, compared, persisted as authority, or used for ordering. The canonical Schema keeps the existing closed `$defs.node` contract unchanged and adds a closed, titled Snapshot-only Node projection at `snapshot.nodes` whose sole additional property is the kind-sensitive `index`. This placement prevents the hint from entering standalone Node, write, operation, and Sync-log contracts while preserving their existing Schema identities and diagnostics.

**Compatibility and migration:** Every previously valid protocol document remains valid because `index` is optional and authoritative Node contracts remain closed against it. Producers may begin emitting the hint only in Snapshot Node representations and should derive it after logical page assembly. Consumers must tolerate omission, stale, mixed, duplicate, and gapped values, continue ordering solely by `position`, and strip the hint before storing or sending authoritative Node state. Producers that formerly used a private out-of-schema field can migrate to the standardized Snapshot-only field without changing Node identity or Sync revisions.

**Tests:** Evidence `core.snapshot-derived-index` covers omission; integer bounds and Root `null`; closed authoritative Node and Snapshot shapes; stale, tampered, duplicated, gapped, and mixed hints; concurrent insertion drift; multiple parents; sparse and paginated projections; duplicate Position refusal; deterministic ASCII ordering; immutable derivation and stripping; and page assembly preservation. Protocol, generated-type, canonical-example, Registry, evidence, and traceability consistency checks cover the synchronized assets and mappings.

## 2026-07-17 - CORE-0020 URL hash wire semantics

**Original problem:** CORE-0020 allowed `urlHash` for duplicate detection and prohibited using it as an object ID, but the canonical Node Schema had no `urlHash` field and the prose did not define its wire syntax, input bytes, placement, or evidentiary meaning. Independent implementations therefore could not exchange or verify the value consistently.

**Why implementation-only was insufficient:** A package-local hash convention could not make an otherwise unknown, Schema-rejected field interoperable. Choosing normalized, canonical, or original URL input independently would also produce different hashes for the same Bookmark while all implementations appeared to follow the original sentence.

**Exact protocol documentation and Schema changes:** `SPECIFICATION.md` and `docs/01-core-data-model.md` now define optional Bookmark `urlHash` as `sha-256=:<padded-base64>:` containing a 32-octet SHA-256 digest over the exact UTF-8 octets of the preserved `url` string. No URL parsing, normalization, or rewriting occurs as part of this algorithm. The canonical Schema adds the closed `urlHash` syntax to authoritative Bookmark Node, Bookmark creation, and Node merge-patch shapes, while excluding it from non-Bookmark and redacted Node forms. A canonical example carries a matching value.

**Identity and compatibility:** Absence remains valid. Producers carrying the field must keep the original `url` and emit a matching digest. Hash equality only selects candidates for further URL, content, and Collection-level comparison; it neither proves duplicate identity nor changes, supplies, or substitutes for any `id`, `collectionId`, or reference. The correction adds a previously unavailable optional field, so existing valid documents remain valid; producers that used private extension hashes may migrate when convenient.

**Tests:** CORE-0020 evidence should cover optional absence, exact UTF-8 hashing and padded syntax, mismatch rejection, original URL preservation, Bookmark-only placement, candidate-only comparison, and separation from all protocol ID fields.

## 2026-07-17 - CORE-0010 Snapshot metadata semantics

**Original problem:** CORE-0010 required Snapshot identity, mode, logical completeness, revision, generation time, pagination state, and a content-digest policy, but the detailed protocol text and Schema left two interoperability gaps. The prose did not state that an `include` query naming every authoritative sidecar array remains logically complete. The body `contentDigest` had no defined syntax, scope, or relationship to the HTTP `Content-Digest` field, and the Schema allowed an arbitrary non-empty string on cropped or paginated representations.

**Why implementation-only was insufficient:** Different conforming servers could mark the same all-inclusive query differently or hash different representations while still satisfying the previous Schema. A client-side convention cannot repair that wire-level ambiguity because producers and consumers need one shared definition.

**Exact protocol documentation and Schema changes:** `docs/02-http-publication-feed.md` now defines `complete=true` for an unfiltered query or an `include` query containing all authoritative arrays (`annotations`, `attachments`, and `relations`), while `root`, `depth`, or omission of any authoritative array makes the projection cropped. `docs/01-core-data-model.md` now limits body `contentDigest` to a complete single-page Snapshot, defines `sha-256=:<base64>:` syntax, defines RFC 8785 canonical JSON coverage over the entire Snapshot excluding `contentDigest` itself, and distinguishes that logical digest from HTTP `Content-Digest`, which covers the actual response bytes. `$defs.snapshotPage` now couples `hasMore` to a non-null `nextCursor`, and `$defs.snapshot` enforces a base64-encoded 32-byte SHA-256 value and single-page complete scope.

**Compatibility and migration:** Previously valid documents with `hasMore=false` and a non-null `nextCursor`, or with a body `contentDigest` on a cropped or paginated Snapshot, are no longer valid. Producers must emit a cursor exactly when another page exists, omit body `contentDigest` from cropped and paginated responses, and recompute single-page logical digests using the defined canonical coverage. Clients must treat `complete` as query completeness rather than page finality, preserve it during assembly, and reject cross-page metadata changes before replacing state. HTTP digest handling remains byte-oriented and is not replaced by the body field.

**Tests:** Evidence `core.snapshot-metadata` covers required metadata and page fields, cursor coupling, logical completeness for `root`/`depth`/partial and exhaustive `include`, cropped multi-page assembly, cross-page identity and metadata stability, body-digest syntax/scope/calculation, and client rejection before assembled state is returned.

## 2026-07-17 - CORE-0011 HTTPS extension namespace authority

**Original problem:** CORE-0011 requires every extension key to be an HTTPS Namespace URI, but the canonical `$defs.extensions.propertyNames` combined generic RFC 3986 `format: uri` validation with only a case-insensitive `https://` prefix. Generic URI syntax permits an empty host in an authority, so keys such as `https://`, `https:///ns`, and `https://user@:443/ns` could satisfy or evade parts of the previous contract without identifying an HTTPS namespace host.

**Why implementation-only was insufficient:** The extension map is a shared wire contract referenced by every extension-bearing core definition. Tightening only the Node implementation would leave other Schema consumers free to accept hostless HTTPS-looking keys, producing incompatible validation results for the same protocol document.

**Exact protocol documentation and Schema changes:** The normative sentence in `SPECIFICATION.md` is unchanged. The canonical Schema retains asserted RFC 3986 `format: uri` validation and now additionally requires the case-insensitive `https://` hierarchical form with a non-empty RFC-valid host, including bracketed IP literals and an optional port. The synchronized Node Schema and semantic validator use the same authority requirement. Arbitrary JSON values under a valid extension key remain unrestricted.

**Compatibility and migration:** Documents containing an extension key with no host, including empty-authority and userinfo-plus-empty-host forms, were invalid under CORE-0011 and are now rejected consistently. Producers must migrate such data to a valid HTTPS namespace URI controlled by the extension owner. Valid HTTPS namespace keys and their payloads require no migration. This correction does not add unknown-extension preservation, synchronization, or export behavior; those obligations remain tracked separately by CORE-0012.

**Tests:** Evidence `core.extension-namespace-uri` covers the canonical shared definition and all extension-bearing Schema references, valid RFC 3986 HTTPS forms, non-HTTPS and relative references, empty and malformed authorities (including userinfo ambiguity), malformed URI syntax, arbitrary nested payload validity, JSON Pointer escaping in semantic errors, and rejection on the public client path.

## 2026-07-17 - CORE-0017 Canonical global resource identity

**Original problem:** CORE-0017 defined global identity as `(serverUuid, resourceType, id)` and required a Canonical URI for cross-server references, but it did not define that URI's grammar, canonical serialization, comparison rules, resource-kind vocabulary, or the context in which a bare ID remains local. Implementations could therefore choose incompatible authority, path, escaping, normalization, and reference forms.

**Why implementation-only was insufficient:** A formatter and parser chosen only by this package would not constrain other producers or consumers. In particular, a `colp://` authority form would subject the case-sensitive `serverUuid` to host normalization and collide conceptually with the MCP Profile's resource locators, while unprefixed `.` and `..` path segments could be collapsed before identity comparison.

**Exact protocol documentation and Schema changes:** `SPECIFICATION.md` now defines the sole identity serialization as `colp:/resources/~{serverUuid}/{resourceType}/~{id}` with no authority, userinfo, port, query, fragment, or percent encoding. Both value components use the existing 1-128 character Wire ID grammar; the kind is exactly one of `collection`, `node`, `annotation`, `attachment`, `relation`, `operation`, or `event`; tuple comparison is field-by-field and case-sensitive. Bare IDs require explicit same-server and expected-kind context. The text and `docs/01-core-data-model.md` distinguish this identity namespace from MCP `colp://{serverUuid}/...` locators. The Schema adds closed `globalResourceIdentity`, enumerated `globalResourceType`, patterned `canonicalResourceUri`, and contextual `globalResourceReference` definitions, plus a synchronized canonical example.

**Compatibility and migration:** There was no previously specified canonical serialization to preserve. Implementations that emitted authority-based, percent-encoded, case-folded, or other ad hoc cross-server references must migrate to the authority-free form. Existing bare references inside a same-Collection Snapshot retain their current meaning and wire representation. MCP resource locator syntax and behavior are unchanged and remain governed by the MCP Profile requirements.

**Tests:** Evidence `core.canonical-resource-identity` covers public root/client/semantic/server exports; all seven kinds; 1/128-character boundaries; every allowed unreserved character; `.` and `..`; exact case; malformed, relative, wrong-scheme, authority, HTTP-lookalike, userinfo, query, fragment, extra/missing segment, Unicode, control, encoded slash/dot/unreserved, double-encoded, invalid-percent, and unknown-kind inputs; claimed-tuple mismatch; local versus foreign resolution; canonical Schema/example definitions; and preservation of same-Collection Snapshot bare references.
