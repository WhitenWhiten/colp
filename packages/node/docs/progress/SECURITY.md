## SEC-0017: public content integrity headers

- Status: accepted locally; bundled conformance evidence remains empty and unverified.
- Implementation: `src/security/content-integrity.ts` primary export `emitContentIntegrityHeaders` (serialization alias: `serializeContentIntegrity`) **emits** frozen RFC 9530 `Content-Digest` and RFC 9421 `Signature-Input`/`Signature` headers for public Snapshot and Feed representations from exact body bytes, a caller-supplied 64-byte Ed25519 signature blob, an active JWKS or Manifest key ID, and non-empty retained rotation IDs. Success disposition is `headers_emitted` — the helper does **not** cryptographically verify Ed25519 signatures.
- Tests: `tests/security/content-integrity.sec-0017.test.ts` has 22 tests covering Snapshot/Feed success (`headers_emitted`), body-byte digest and Base64 padding, fixed signature components, HTTPS target and media-type validation, Ed25519 byte-length and key-source shape checks, active/retained rotation, malformed/header-injection input, non-public short-circuit, hostile structured input, immutable secret-safe headers, and no network or stale-resource behavior.
- Security review: public applicable inputs are descriptor-snapshotted from plain or null-prototype data, raw signature bytes are exactly 64 bytes (length only), generated headers contain only fixed components and bounded key identifiers, and non-public/other resources return `not_applicable` before reading residual secret fields. JWKS/Manifest retrieval and cryptographic verification remain adapter responsibilities; naming deliberately avoids `enforced` for this emit-only path.
- Scope boundary: mutable-resource signed fields, maximum staleness, historical Release URIs, route/header attachment, key retrieval, signature verification, Publisher HTTP, MCP write, sync, feed, schema, CORE semantics, and generated types remain outside this requirement and SEC-0018 owns the stale-resource contract.

## SEC-0018: mutable publisher integrity and historical release URIs

- Status: accepted locally; bundled conformance evidence remains empty and unverified.
- Implementation: `src/security/mutable-integrity.ts` snapshots a canonical five-component mutable claim envelope (`@status`, `created`, `expires`, `etag`, and protocol version), verifies it through a native-Promise boolean port, then reads the clock and enforces a bounded maximum staleness window — success disposition `enforced` / reason `mutable_integrity`. Historical releases perform **shape/URI validation only** (immutable flag, Release ID and Revision presence, exact canonical HTTPS URI without query, fragment, default port, host-case, dot-segment, or percent ambiguities) and return disposition `shape_validated` / reason `historical_release` with no cryptographic verify.
- Tests: `tests/security/mutable-integrity.sec-0018.test.ts` covers claim omission, duplicate/reorder/extra/mutation, frozen token-free verification input, Promise and receiver/TOCTOU behavior, timestamp and safe-integer boundaries, historical URI canonicalization with `shape_validated`, mutable crypto path with `enforced`, hostile object shapes, non-applicable residual isolation, and frozen deterministic decisions.
- Security review: all structured inputs and port methods are descriptor-snapshotted from ordinary plain records; accessors, Proxy/custom/inherited/sparse/dynamic values, hostile Promise/clock results, and malformed claims fail closed. Signature verification occurs before the freshness clock read on the mutable path only; historical-release does not consult the signature port. No signature material or claim contents are returned in decisions. Route wiring, key retrieval, cryptographic verification, and network behavior remain adapter responsibilities.
